## Search Console 수치와 차이가 나는 이유

1. **집계 대상이 다르다.** Search Console 검색 실적의 클릭은 Google 검색 결과에서 사이트로 이동한 횟수이며, 노출은 검색 결과에 사이트가 표시된 횟수다. 직접 접속, 북마크, 메신저·커뮤니티 링크와 다른 검색엔진 유입 전체를 나타내지 않는다. 계정 수와 검색 노출 수는 직접 비교할 지표가 아니다. [Google 공식 설명](https://support.google.com/webmasters/answer/7576553?hl=en)
2. **이 앱은 페이지를 열면 익명 인증을 시작한다.** 현재 코드와 10월 29일 변경 이전 코드 모두 `onAuthStateChanged`에서 기존 사용자가 없으면 `signInAnonymously()`를 호출한다. 타이머 버튼을 누를 필요가 없다. 따라서 계정 생성은 방문 및 인증 요청에 가까운 신호이고, 기능 사용을 보장하지 않는다. [Firebase 익명 인증 문서](https://firebase.google.com/docs/auth/web/anonymous-auth)
3. **익명 계정과 실제 사람은 일대일이 아니다.** 이 프로젝트는 Firebase 기본 브라우저 인증 지속성을 사용한다. 같은 출처의 일반적인 재방문은 기존 인증을 재사용하지만, 다른 브라우저·기기·사이트 출처, 시크릿 세션 또는 사이트 데이터 초기화에서는 동일인이 여러 UID를 만들 수 있다. JavaScript를 실행하는 자동화나 익명 가입 API 호출도 계정을 만들 수 있다. 현재 데이터만으로 그 비율을 산정하지 않았다. [Firebase 인증 지속성 문서](https://firebase.google.com/docs/auth/web/auth-state-persistence)

사용자가 제시한 ‘최근 1주 클릭·노출 각각 100 미만’은 제공받은 정보로 사용했다. Search Console 보고서를 직접 조회하거나 기간·속성·검색 유형 설정을 검증한 것은 아니다. 이번 분석에서는 Auth와 Firestore에 관측된 실사용을 검증했다.

## 집계 검증과 한계

- Authentication 계정 3,246개를 모든 페이지에서 조회했고, 이 중 10월 생성 3,102개는 모두 연결된 로그인 제공자가 없는 익명 계정이었다. `lastLoginAt`이 생성 시각과 같아 이 필드로 재방문을 집계하지 않았다.
- Firestore 최상위 컬렉션 3개(`dailyRankings`, `activeSlackers`, `rankings`)를 확인했다. 10월 날짜별 랭킹 문서 1,140개와 활동 문서 1,776개를 페이지 끝까지 조회했다. `rankings`의 5개 문서는 5월 기록이어서 10월 집계에서 제외했다.
- 랭킹 문서 1,140개 중 1,062개에 양수 시간이 있으며, 78개는 시간 필드가 없다. 닉네임만 저장해도 랭킹 문서가 생길 수 있으므로 문서 수를 그대로 실사용자 수로 세지 않았다. 날짜 경로와 UID로 중복을 제거했다.
- 10월 양수 시간 저장 UID 961개는 모두 10월 활동 흔적 집합에 포함됐다. 관측된 활동·저장 UID는 모두 Authentication에 존재하고 UID 필드는 문서 ID와 일치했다.
- `activeSlackers`는 UID별 마지막 상태로 덮어쓴다. `createTime`은 첫 시작의 근거지만, 모든 날짜별 시작·중지 이력을 복원할 수 없다. 과거 정확한 DAU나 세션 수는 계산할 수 없다.
- 저장 시간은 타이머의 경과 시간이다. 백그라운드 실행도 포함할 수 있으며 실제로 화면을 보거나 조작한 시간을 뜻하지 않는다. 5분 기준도 사람과 봇을 구별하는 기준은 아니다.
- 10월 9일 문서 1개에 60,626초(약 16시간 50분)가 저장돼 현재 일일 상한 50,400초를 넘었다. 과거 클라이언트 누적 처리나 입력 검증의 영향을 배제할 수 없다. 이 문서의 UID는 한 번만 계산했고, 원본을 수정하거나 봇으로 제외하지 않았다. 일별 시간을 상한으로 잘라도 이 보고서의 주요 UID 수와 1분·5분·10분·1시간 임계값 집계는 바뀌지 않는다.
- 랭킹 날짜와 서버 생성일(KST)이 다른 문서 8개, 최종 갱신일이 다른 문서 12개가 있다. 과거 코드의 브라우저 시간대 및 늦은 저장 영향이 가능하다. 일별 사용 기록은 랭킹 날짜 경로를 기준으로 집계했으며 자정 인접 일자별 수치는 오차 가능성이 있다. 월간 UID 중복 제거에는 같은 UID를 한 번만 반영했다.
- 계정·문서 삭제, 기록 변조, 브라우저 저장소 초기화 및 테스트 계정을 완전히 식별할 수 없고 실제 사람 수의 상한·하한을 통계적으로 제시할 근거가 없다. 보고서의 모든 이용자 수는 관측된 UID 수다.

## 이후 측정 기준

운영 대시보드에는 ‘신규 익명 계정’, ‘타이머 시작 고유 사용자’, ‘시간 저장 고유 사용자’, ‘5분 이상 저장 고유 사용자’를 각각 표시하는 것이 적절하다. 10월의 대표 실사용 수치로는 **양수 시간 저장 961개 UID**, 그중 지속 사용을 확인하는 보조 지표로는 **5분 이상 254개 UID**를 사용할 수 있다.

정확한 유입 원인을 찾으려면 해당 시간대의 Vercel 방문·리퍼러·봇 관련 로그나 별도 웹 분석 데이터가 필요하다. 앞으로는 사이트 개인정보 안내와 측정 동의를 검토해 유입 경로와 `timer_start`, `timer_pause`, `timer_finish`, `ranking_saved` 이벤트를 기록하면 신규 방문, 기능 전환, 반복 사용을 구분할 수 있다. Firebase 익명 인증을 첫 서버 기능 사용 시점으로 미루는 변경은 불필요한 계정 생성을 줄일 수 있지만, 유입 경로 측정이나 봇 판별을 대신하지는 않는다. 이번 작업에서는 코드나 운영 설정을 변경하지 않았다.
